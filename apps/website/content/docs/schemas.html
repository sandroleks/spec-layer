The canonical schemas define the full Context v5 artifact. Use them when validating exports or building tools that consume Spec Layer data.

The schema identifiers are the component schema URI and the foundation schema URI. Their v5 paths identify the major contract; check spec_layer.schema_version for the exact artifact version.

Validate canonical JSON against these schemas. Component clipboard YAML, foundation DTCG JSON, and the outer library bundle are different shapes.

Get a canonical artifact

After pulling a library, add --canonical to show. Redirection below saves the JSON to a local file.

npx spec-layer show component Button --canonical > button.json
npx spec-layer show foundation --canonical > foundation.json

Use your component’s actual name. The canonical envelope includes spec_layer.kind, schema_version, schema_uri, extractor metadata, export metadata, and source identity.

Validate outside the plugin

Use a validator that supports Draft 2020-12, such as Ajv’s 2020-12 implementation. Save both schemas, a canonical button.json, and the example validation script in your project. The component schema references definitions in the foundation schema, so pass it as a dependency:

npm install --save-dev ajv
node validate-context.mjs component-context-v5.schema.json button.json foundation-context-v5.schema.json

To validate a foundation, pass its schema and canonical artifact:

node validate-context.mjs foundation-context-v5.schema.json foundation.json

The script loads the files you supply and does not fetch schemas from the network. It exits with 0 on success and 1 on a schema, data, or file error. This is a standalone validation example, not a Spec Layer CLI command.

What schema validation tells you

It checks structural requirements such as required fields and supported value shapes. It does not by itself establish that every Figma source was readable, all references resolve, or an interface is accessible.

Inspect diagnostics and reference status alongside schema validity. The extractor separates structural checks from referential integrity and completeness concerns.

Identity and content hashes

Use stable source IDs for identity. Names may change or collide. A component binding uses both resource kind and source ID; a token value is associated with a mode ID rather than only a mode name.

spec_layer.export.content_hash identifies semantic content. Export timestamps, export IDs, generated prose, and diagnostic wording do not define that identity. Component context also identifies the full source foundation and the dependency slice it uses.

Canvas drift hashes are separate from exported semantic hashes. Do not treat every metadata change as a design change or use a whole-foundation hash as a substitute for a component’s own content hash.

Library bundle version

The published bundle has its own envelope: schema: "spec-layer-library-bundle" and version 1.0.0. It contains foundation and component entries with their projections and canonical artifacts.

The ai field in a foundation entry contains the serialized DTCG JSON document; in a component entry it contains YAML. Despite the shared field name, the formats differ.

The current CLI reads bundle major version 1. The bundle parser checks the transport envelope; that is separate from validating each canonical Context artifact. See the bundle contract for the exact structure.
