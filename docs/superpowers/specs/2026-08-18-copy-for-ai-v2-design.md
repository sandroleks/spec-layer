# Copy for AI v2: a correct, legible brief

**Date:** 2026-08-18
**Status:** Proposed
**Packages:** `packages/extractor`, `packages/plugin`
**Responds to:** `Spec_Layer_Component_Spec_Schema_v2.docx` (external proposal)
**Builds on:** `2026-08-14-copy-for-ai-design.md`

## Summary

Copy for AI v2 copies the same information the plugin already has, correctly and
legibly. It fixes four defects that make today's payload wrong or empty, and it
restructures the YAML so a model reads each fact once instead of thirty-six
times.

It adds no new generated content. The only generated text in either brief is
prose the plugin has already produced and already shows on a frame: component
guidelines, and foundation group descriptions. Every other field is a value read
from the Figma file.

The v1 format is unreleased, so v2 is a free breaking change.

## Problem

The intended workflow has two steps:

1. Copy the **foundation brief**. The agent learns the token vocabulary and what
   each group is for.
2. Copy a **component brief** per component. The agent gets that component's
   contract, referencing tokens by the names step 1 introduced.

Both steps are currently degraded.

### Step 1 drops everything the plugin generated

The foundation frame renders AI-written per-group descriptions, generated by
`buildGroupPrompt` / `parseGroupResponse` and persisted on the doc link as
`FoundationDocLink.groupDescriptions` (`docLink.ts:180`). `foundationBrief()`
(`brief.ts:66`) emits only `spec_layer`, `source`, `collections` and
`text_styles`. None of the descriptions reach the clipboard, so the step whose
whole purpose is "set the foundation" hands over a bare token table.

### Step 2 is wrong in four ways

**Contrast never runs.** `checkContrast` takes its text parts from
`spec.anatomy` (`contrast.ts:291`), and `extractAnatomy` stops its walk at
`INSTANCE` boundaries (`anatomy.ts:100`). A component whose label is a nested
instance therefore has zero TEXT parts, so the loop body never executes and the
brief reports `measured: 0, skipped: 0`. That reads as "nothing to report" when
it means "nothing was checked". On the sample Button this hides two real AA
failures: `surface/primary/disabled` against white at 2.23:1, and
`surface/primary/light-press` against `text/primary/default` at 4.22:1.

**Two part vocabularies.** `anatomy` names parts `iconLeft` / `ButtonLabel` /
`iconRight`; token rules name them `Container` / `Label` / `Vector`, because
`extractTokens` walks through instances via `walkParts` while anatomy does not.
Nothing can join the two. This is the root cause of the contrast defect above,
and of `unbound` reporting `ButtonLabel: hardcoded color` while `tokens` shows
`Label` fill bound to a real token.

**Part names are not identities.** `siblingPartNames` disambiguates only among
siblings (`naming.ts:31`), so `header > label` and `footer > label` are one name.
`contrast.ts` already detects this and skips such parts rather than guessing;
the underlying ambiguity remains.

**Values ignore modes.** `lookupToken` resolves at the owning collection's
default mode (`brief.ts:215`) while `layout` reports rendered geometry. On the
sample Button that produces a flat contradiction: `layout` says `radius 4`,
`base` says `rd-sm` resolves to `8`. Nothing marks which is authoritative or
which mode a `resolved:` value belongs to.

### And it is too long to read

`by_variant` emits the full cross product. Every one of 36 entries repeats
`padding-x`, `gap`, `height` and `typography`, though those depend only on the
size axis, and every colour binding is byte-identical between Large and Small.
The `tokens` block is roughly 2,400 of the sample's ~2,700 lines. The Copy
action already warns above 800 lines (`actions.ts:599`), which is an admission
that the payload does not fit the surface it is aimed at.

## Goals

- Every fact the plugin already knows reaches the clipboard, including generated
  prose in both briefs.
- Contrast actually measures, and says honestly when it could not.
- One part identity, shared by anatomy, token bindings, gaps and contrast.
- Resolved values state which mode they belong to.
- A 36-variant component fits in roughly 400-500 lines with nothing lost.
- Generated text is confined to one clearly named block per brief.
- No new runtime dependency in the plugin bundle.
- Existing doc-link hashes do not move, so no canvas doc reports false drift.

## Non-goals

Everything here is cut because it would require generating facts the Figma file
cannot prove, or because it is a different product:

- `implementation_readiness` score and category subscores.
- `state_precedence`, `state_rules`.
- `behavior.*`: cursor, keyboard keys, pointer behaviour, events.
- `content.*`: label word counts, text expansion percentages, RTL rules.
- `accessibility.semantics` recommendations, `interface.element`, aria advice.
- `component.identity.category` / `status`, invented `related` components.
- `focus_ring.offset`, which has no Figma equivalent.
- Generating production code, MCP or hosting, library-wide bundles.
- Changing the canvas frames, or changing any prose prompt.

## Principles

1. **Copy, do not invent.** A field exists only if a Figma read or an
   already-stored generation produces it.
2. **One identity per part.** Anatomy, bindings, gaps and contrast all key on the
   same string.
3. **Say unknown.** `unknown`, `not-measured` and an absent key beat a plausible
   default.
4. **Compress by condition, not by repetition.** The extractor already computes
   minimal variant conditions; emit them instead of expanding them.

## Design

### Part identity: the keystone

Introduce a **part path**: the sibling-disambiguated names from the component
root down to the node, joined with `/`.

```
Container
Container/iconLeft
Container/ButtonLabel
Container/ButtonLabel/Label
```

One walk produces it, and `TokenRule`, `Gap`, `AnatomyPart` and the contrast
check all carry it. `part` (the bare leaf name) stays for display; `path` is the
identity every join uses.

A layer name may itself contain `/`, which would make a joined path ambiguous, so
a literal `/` in a segment is escaped as `\/` when the path is built. Escaping at
construction keeps the identity a single readable string, which a joined path
needs to be if a model is to match a binding against an anatomy entry by eye.

This fixes the vocabulary split structurally rather than by convention: tokens
walking deeper than anatomy is fine, because a deeper path is still a valid
identity and the anatomy tree is simply a bounded view of the same namespace.

**Hash compatibility.** `specContentHash` hashes `spec.tokens` including `part`
(`hash.ts:42`), so adding `path` to `TokenRule` would flip every committed doc's
hash and light up spurious "update available" badges on canvas. The projection
inside `specContentHash` therefore reduces each `TokenRule` to its legacy
`{part, property, conditions, token}` shape before hashing, exactly as it
already reduces `anatomy` to the legacy depth-0 shape. A test asserts the hash
of a fixture spec is unchanged from v1.

### Envelope and source

```yaml
spec_layer:
  kind: component
  version: 2
  extractor: "1"
  generated: 2026-08-18T09:14:02.113Z
source:
  file_key: 6ddb9fbd28c4...
  file_name: Design System
  node_id: "1391:54066"
  node_name: buttonPrimary
  component_key: 6ddb9fbd28c4...
```

`figmaFile` today holds a file *key* under a field named `file`, and falls back
to the literal string `unknown` when the key is unavailable
(`fileKey.ts:15`). v2 splits key from name and **omits** either key rather than
emitting `unknown`, so an absent value reads as absent.

### API: variants separated from states

```yaml
api:
  variants:
    type: { options: [Primary, Outline, Ghost], default: Primary }
    size: { options: [Large, Small], default: Large }
  states: [hover, focused, pressed, disabled, loading]
  booleans:
    iconLeft: { default: true }
    iconRight: { default: true }
```

The split is deterministic: `detectStateMatrix` already classifies state-like
axes. v1 emitted the same information three times (`api`, `axes`, `states`) and
its `axes` block implied 3 x 2^5 = 384 combinations against 36 real variants.

`detectStateMatrix` has a known weakness: `STATE_ORDER` contains `error`,
`danger`, `warning` and `success`, so a `Tone = Success | Warning | Error` axis
is read as an interaction-state matrix, and when several axes match it silently
takes the first. v2 does not change the detection, but when more than one axis
matches it emits a `validation` finding naming the axes, so an ambiguous read is
visible rather than silent.

### Anatomy

A tree, carrying paths:

```yaml
anatomy:
  - part: Container
    path: Container
    type: COMPONENT
    children:
      - part: iconLeft
        path: Container/iconLeft
        type: INSTANCE
        component: iconWrapper
      - part: ButtonLabel
        path: Container/ButtonLabel
        type: INSTANCE
        component: ButtonLabel
```

Unchanged in depth and content. Only `path` is added.

### Tokens: definitions once, bindings by condition

Two blocks. `used` lists every token this component references, resolved per
mode. `bindings` says where each one applies.

```yaml
tokens:
  used:
    color/surface/primary/default:
      alias: colors/blue/500
      resolved: { Light: "#722ed1" }
      code: { WEB: "--color-surface-primary-default" }
    button/lg-height:
      alias: spacing/900
      resolved: { Light: 36 }
  bindings:
    - path: Container
      property: fill
      token: color/surface/primary/default
      when: { type: [Primary], size: [Small] }
    - path: Container
      property: height
      token: button/lg-height
      when: { size: [Large] }
    - path: Container
      property: border-radius
      token: rd-sm
```

`when` is the **minimized condition the extractor already computes** in
`TokenRule.conditions`, listing only the axes a binding actually depends on. An
absent `when` means every variant.

v1 discarded these conditions and resolved bindings per variant, on the argument
that the consuming model should never evaluate a condition. The cost was
thirty-six near-identical copies of every geometry and colour binding. A `when`
map is a lookup, not a boolean expression, so the readability argument is
satisfied without the duplication.

This also replaces the external proposal's separate `by_size` and `visuals`
blocks, which duplicate each other and require the extractor to know which axis
means "size". Conditions need no such knowledge.

**Modes.** `resolved` is a map keyed by mode name. Single-mode collections emit a
single entry rather than a scalar, so the shape never changes. Where a rendered
geometry value disagrees with its bound token's resolved value, `validation`
carries a finding rather than the brief silently presenting both.

**Property naming.** `border` today means stroke colour while `border-radius`
means geometry. v2 uses `border-color` for the paint.

### Typography

```yaml
typography:
  "Button/L":
    source_name: "Button/L : 14px Medium"
    font_family: Inter
    font_size: 14
    font_weight: 500
    line_height: { unit: PIXELS, value: 20 }
    letter_spacing: { unit: PIXELS, value: 0 }
```

Resolved from `FoundationSpec.textStyles`, which is already captured. v1 emitted
only the display string, so nothing downstream could act on it, including
`requiredRatio`, which needs size and weight to pick a WCAG threshold.
`source_name` preserves the raw Figma style name, including its stray double
spaces.

### Layout

Base geometry of the default variant, with any per-variant geometry expressed as
token bindings like everything else:

```yaml
layout:
  direction: horizontal
  align: center
  radius: { value: 4, token: rd-sm, mode: Light }
```

Every numeric value states the mode it was read in. `value` is what the frame
renders; the token it names resolves to `8` in `tokens.used`. v2 emits both and
raises a `geometry-token-mismatch` finding, rather than presenting one number in
`layout` and a different one under `tokens` with nothing connecting them.

### Unbound

```yaml
unbound:
  - path: Container/ButtonLabel
    property: itemSpacing
    value: 8
    issue: hardcoded-value
```

Keyed on `path` and on a named property, so it can be cross-checked against
`bindings`. Any gap whose path and property already appear in `bindings` is
dropped, which removes the current contradiction where `unbound` claims
`ButtonLabel` has a hardcoded colour while `bindings` shows the token.

### Contrast

`checkContrast` sources text parts from a full-tree walk keyed on `path`, not
from the bounded anatomy list. Reporting shape is unchanged:

```yaml
contrast:
  measured: 14
  skipped: 0
  findings:
    - path: Container/ButtonLabel/Label
      variant: "type=Primary, size=Large"
      foreground: "#ffffff"
      background: "#a9aeb8"
      background_path: Container
      ratio: 2.23
      required: 4.5
```

### Validation

Deterministic findings only. Each is computed, never inferred:

| id | what it detects |
|---|---|
| `default-state-uses-state-token` | a default variant bound to a token whose name carries another state, e.g. Primary/Large/Default on `surface/primary/disabled` |
| `geometry-token-mismatch` | a rendered value disagreeing with its bound token's resolved value, e.g. radius 4 against `rd-sm` = 8 |
| `duplicate-conflicting-binding` | one path and property bound to two different tokens in the same variant |
| `ambiguous-state-axis` | more than one axis matched `detectStateMatrix` |
| `contrast-failure` | mirrors each contrast finding |
| `unbound-value` | mirrors each `unbound` entry |

```yaml
validation:
  - id: default-state-uses-state-token
    severity: warning
    path: Container
    property: fill
    message: >-
      The default variant binds fill to color/surface/primary/disabled.
    when: { type: [Primary], size: [Large] }
```

No aggregate score. Severities are `warning` and `error` only; there is no
`info` tier, because a finding nobody should act on should not be emitted.

### Guidelines: the generated boundary

Because generation is confined to prose, the boundary is a single block rather
than a per-field annotation:

```yaml
guidelines:
  origin: generated
  definition: ...
  accessibility: ...
  interactions: ...
  variants_summary: ...
  anatomy_summary: ...
  content_considerations: ...
  dos: [...]
  donts: [...]
```

Content is passed through verbatim from storage, exactly as today. The only
change is the `origin` marker and the guarantee that no generated text appears
anywhere else in the document.

One consequence worth stating: generated prose can contradict extracted values,
as it does today when the guidelines recommend a 44px touch target for a button
the same brief measures at 36px high. v2 does not edit prose to fix this. It
emits a `validation` finding when a guideline numeral contradicts a measured
value, leaving both visible.

### Foundation brief

```yaml
spec_layer:
  kind: foundation
  version: 2
collections:
  - name: Primitives
    modes: [Light]
    default_mode: Light
    tokens: [...]
text_styles: [...]
guidelines:
  origin: generated
  group_descriptions:
    Primitives:
      color/surface: "Surfaces you paint panels and controls with."
      spacing: "The 4px step scale layout and component padding are built from."
```

Descriptions are read from the `FoundationDocLink.groupDescriptions` of the
foundation docs present on canvas and merged across docs. Two collections can
each have a folder of the same name, so the merge key is collection name plus
folder path, matching how `descriptionsForUnit` (`main.ts:415`) splits a
build-wide map back out per unit. `group_descriptions` is therefore nested under
its collection, not a flat folder map.
They are partial by nature: `copyFoundationBrief` deliberately covers the whole
file while a foundation doc may cover one scope, and a file may have no
foundation doc at all. Groups without a description simply have no entry, and
the block is omitted entirely when there are none. Nothing is generated at copy
time.

## Testing

The extractor is pure, so everything below runs under vitest without Figma.

- **Part paths:** siblings with one name, nested instances, depth jumps, a
  component set root, a bare component root.
- **Hash stability:** `specContentHash` of a v1 fixture is byte-identical after
  the `path` field is added.
- **Contrast:** a fixture whose label is a nested instance measures a non-zero
  pair count, and the known-failing Button pairs produce findings at 2.23 and
  4.22.
- **Bindings:** a binding depending on one axis emits a one-axis `when`; a
  universal binding emits none; two rules colliding on path and property emit a
  `duplicate-conflicting-binding` finding.
- **Modes:** a two-mode collection emits both, a one-mode collection emits one.
- **Unbound:** a gap whose path and property are bound is dropped.
- **Foundation:** descriptions merge across two docs, partial coverage keeps the
  extracted half intact, no docs omits the block.
- **Boundary:** a scan asserting no key outside `guidelines` carries generated
  text.
- **Size:** the Button fixture brief is under 600 lines. The target is 400-500;
  the assertion sits above it as a regression guard, not as the goal.
- **Golden file:** the full Button brief, reviewed once by hand, then diffed.

## Risks and open questions

- **Mode pairing is unsolved.** Text and background can live in different
  collections with different mode sets, so per-mode contrast checking still needs
  its own design. v2 keeps measuring at the default mode and now says so.
- **Path churn.** Renaming a layer in Figma changes a path and therefore every
  binding that mentions it. This is correct behaviour for drift detection but
  makes diffs noisier than name-only identity did.
- **Partial foundation descriptions** may read as an incomplete vocabulary. The
  alternative, generating at copy time, is excluded by scope.
- **Unverified in Figma.** v1 was code-complete and fully reviewed but never run
  in Figma. v2 must not repeat that: a manual pass in a real file is a release
  gate, not a follow-up.

## Sequencing

**P0 — the brief is wrong without these.** Ships on the current schema; no
format break.

1. Part paths threaded through tokens, gaps, anatomy and contrast, with the hash
   projection that keeps `specContentHash` stable.
2. Contrast walks the full tree so it measures.
3. Foundation brief carries its stored group descriptions.
4. `unbound` reconciled against bindings.
5. Mode-aware resolved values.
6. `source` split into key, name, node and component key.

**P1 — the format change.** One breaking bump to `version: 2`.

7. `tokens.used` plus condition-based `tokens.bindings`.
8. `api` split into variants, states and booleans.
9. Typography resolved structurally.
10. `validation` block.
11. `guidelines.origin` and the generated-content boundary.
12. Size assertion and the golden-file test.

P0 is independently shippable and worth shipping alone if P1 slips.
